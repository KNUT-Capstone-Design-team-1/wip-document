# 데이터 동기화

수동 검증 시나리오입니다. 코드 대조로 정리했으며 기기에서 통과한 결과를 의미하지 않습니다.

| 구분                   | 확인 절차 및 기대 결과                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 최초 설치              | 9개 리소스 테이블과 로컬 사용자 테이블이 초기화되고 필수 업데이트를 완료한 뒤 메인으로 진입한다.                                            |
| 기존 설치              | 스키마·데이터 버전을 비교하고 변경된 테이블만 업데이트 대상으로 표시한다.                                                                   |
| 선택 업데이트          | 확인 모달에서 진행 시 다운로드하고 거절 시 메인으로 진입한다.                                                                               |
| 새 건강기능식품 테이블 | 두 건강기능식품 테이블 중 기존 스키마 버전이 0인 업데이트는 필수 진행한다.                                                                  |
| 캐시·진행률            | 페이지 병렬 다운로드 중 진행률과 파일 캐시·저장 상태가 갱신된다.                                                                            |
| 캐시 검증              | 페이지 누락·잘못된 응답 구조를 검출하고 실패 처리 후 재시도한다.                                                                            |
| 적용 검증              | 기대 건수가 양수인데 삽입 결과가 0건이면 검증 실패한다. 현재 코드는 전체 건수 일치까지 검사하지 않으며 검증 통과 후 테이블 버전을 갱신한다. |
| 실패·복구              | 통신·적용 오류 시 실패 상태·재시도를 확인한다. 실패한 삽입 트랜잭션의 롤백과 전체 업데이트의 원자적 롤백을 구분한다.                        |
| 중단·복귀              | 다운로드·설치 중 앱을 종료하고 재실행하여 중단 상태를 감지하고 다시 진행하는지 확인한다. 포그라운드 복귀 시 저장 진행률이 반영된다.         |
| 사용자 데이터          | 공공 리소스 갱신 후에도 보관 폴더·저장 항목·복용 일정이 유지된다.                                                                           |
| 완료                   | 캐시·상태가 정리되고 초기화 화면을 종료한다.                                                                                                |

구현 근거: `src/features/database_update/services/`, `src/features/database_update/utils/updateCheck.ts` (앱 저장소).
